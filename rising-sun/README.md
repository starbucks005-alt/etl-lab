# The Rising Sun

An artificial sunrise made of acrylic and LED strips, with a light fairy inside who talks to you. Started 2026-10-18, Dr. O's design.

## What it does
1. At the wake time the strip climbs from dark red to amber to full daylight over about 30 minutes (`sunrise.ino`, on an ESP32-S3 board, no Pi).
2. When the sun is up the fairy greets you: "Good morning, human." (`personas.json`). One fairy for now (Dr. O, 2026-10-18: keep it simple, build up as interest happens). Her voice is an ElevenLabs voice id that Dr. O picks and pastes on the panel. Until she does, she shows words and makes no sound. The code can still hold more fairies later.
3. She asks: "Good morning sunshine. Do you want to hear the news, check your calendar, or something else?" (`morning.py`)

## What exists, and what does not

- NOT TRIED ON THE REAL BOARD OR LEDS. The color steps are a first guess. Run `python3 sunrise.py` to see them, then look at the real strip and tell Claude what is wrong. `sunrise.ino` holds the same table and the wake time.
- The panel: `rising-sun/panel.html`, at emerging-tech-lab.com/rising-sun/panel.html (it was `index.html` until 2026-10-19, when the web page took that name). Modelled on the Astra-9 Lite panel. Enter the key once. It sets the wake time, sunrise length and time zone, picks the fairy, lets you change a fairy's greeting, question, manner, backstory and voice or make new ones, previews the sunrise, lets you talk to her, and saves your calendar link. Settings are saved by `netlify/functions/sun-settings.js` and read by the brain and by the board.
- Checked: the panel in a real browser against the real handlers with a stand-in store (`node tests/sun-settings.test.js`). NOT tried on the live site or the board.
- NOT BUILT: her voice and her listening on the board itself. With no Pi these go through the website, the way the Holopod page does. `morning.py` is the flow written out so it can be checked; it is the plan for that page, not code that runs on the board.
- The news is Above the Fold from ETL Newswire (Dr. O, 2026-10-18). Asked for the news, she says one line and the brain returns the recorded briefing's address, its headlines and its length; the panel and the board play the briefing itself. If today's has not come out she says so and offers the last one. Read from `newswire_briefings_meta/latest`, the same record the home page player uses. Checked with stand-ins only; not tried against the live record.
- Calendar: the link is saved on the website and never shown again, the way AL keeps hers. Nothing reads it yet. AL's calendar reader is Python and has not been ported.
- Her backstory is empty until Dr. O writes it. Anything not written there gets a short "I don't know that one".
- The acrylic and strip layout (how many LEDs, rings or a disc) is not decided, so `LED_COUNT` in `sunrise.ino` is a placeholder.

## The brain is in the cloud (2026-10-18)
Dr. O: "can be a brain in the cloud like the figurines." The board only runs the light, and asks the website what the fairy says.
- `netlify/functions/sun-morning.js` is that brain. `step: "wake"` returns the greeting and the question. `step: "answer"` with `heard` returns her reply. With `audio: true` it also returns her voice as base64 mp3 from Azure.
- Every call needs the header `x-sun-key` to match the sun's access code, because each answer can spend Azure and Anthropic credits. With no key set it answers 503. The key is not in the repository: set it in Netlify and put the same value on the board.
- The calendar is not connected, and she says so. The news plays Above the Fold. "Something else" goes to Claude with the fairy's own lines. Her written backstory is empty, so the prompt tells her to say she does not know that one.
- Her voice: ElevenLabs, with the key the site already has (`_eleven.js`, the same call `gc-voice.js` makes). Not chosen yet, and not tried against the real service.
- Credits (Dr. O, 2026-10-18: use the AWS and Azure startup credits when possible): her voice is Azure, so the Azure credits pay (the site's existing Azure key, read the way gc-voice reads it). Her thinking tries Claude on Amazon Bedrock first, so the AWS credits pay (`_bedrock.js`), and falls back to Anthropic's own API (the key the site already has). The Bedrock key is pasted once on the panel's Connections card and kept in the sun's private record, because the site is at its limit of environment variables. Netlify refused a new environment variable (over the limit, 2026-10-18), so the access code is kept as a fingerprint in the same private record, set once from the panel's access code card in owner view through `gc-config.js` (`set_sun_key`, needs the owner key). `SUN_DEVICE_KEY` still works if a variable ever is set, and wins over the private record. The Bedrock model id and the account's access to the model are not checked: make one call and see.
- Her settings sit in Netlify's own small store, which is free at this size. Moving them to Azure Storage would count toward the Azure milestone only if that workload needs the spend, which is not worth doing for one small record.
- Checked with stand-ins: `node tests/sun-morning.test.js`. NOT tried against the real services or from the board.
- Still open: how the board hears you and plays her voice. It needs a microphone and a speaker amplifier on the ESP32-S3, and a way to turn mp3 into sound. Until that is built the page route (a tablet) is the way to hear her.

## Music (Dr. O, 2026-10-18)
- The panel plays Apple Music with Apple's web player (MusicKit JS). The listener signs in with their own Apple Music subscription, so ETL pays nothing for the music. Without a subscription only short previews play. It plays on the device that has the panel open, such as a tablet beside the sun. A browser needs a tap first, so music cannot start by itself at wake time.
- Setup: the Team ID, the Key ID and the private key (.p8) from Dr. O's Apple developer account, pasted once under Connections. They are kept in the sun's private record and never shown again. `netlify/functions/sun-music-token.js` signs a short-lived token with them (`_apple.js`, Node's own crypto, no new packages and no new environment variable). The sheet "Rising-Sun_Apple-Music-Key" says how to make the key.
- Checked: the signing against a key made for the test, and the player in a real browser against a stand-in for MusicKit (`node tests/sun-apple.test.js`). NOT tried against Apple. Whether Apple accepts the token depends on the real key and its Media ID.
- Spotify (Dr. O, 2026-10-18): the panel signs in with Spotify's PKCE flow, so no secret exists anywhere; only the public Client ID is saved (`spotify.js`, `tests/sun-spotify.test.js`). The listener needs Premium. The panel can play on itself in a computer browser (Spotify's web player; from memory it does not run in phone or tablet browsers) or act as a remote for any other Spotify device, so a phone works. The tokens stay in the signing-in browser. A new Spotify app is in development mode, where only people added by hand can sign in, and from memory the limit is small and wider access is hard to get, so check Spotify's current rules before selling it. The sheet is "Rising-Sun_Spotify-App". NOT tried against Spotify; the stand-in test covers sign-in, devices, search, play, pause, next and playlists.
- Not built: music coming out of the sun's own speaker (it could appear as a Spotify device later). Amazon Music has no open player that I know of.

## What a customer sees, and what only ETL sees (Dr. O, 2026-10-18)
- ETL holds every provider key (thinking, voice, music setup) and pays for them. A customer never types or sees a key. A customer signs in to their own Apple Music or Spotify account, and later will see their plan and credits (not built).
- The panel has an owner view for ETL only: add `?owner=1` to the address. It lasts for that browser tab only, shows a bar saying "Owner view" with an Exit button, and ends when the tab closes. `?owner=0` also turns it off. It shows the "Owner setup" section (Bedrock key, Apple key, Spotify Client ID) and the voice id and picture boxes on each fairy. A customer's view has none of them. This is a view, not a lock: the real protection today is that every call needs the sun's access code. Before units are sold, each sun needs its own access code and the provider keys must be writable only with an ETL owner credential, not a customer's.

## Parts
ESP32-S3 N16R8 (as in the Holopod box), WS2812B strip, its own 5V supply sized for the strip, a speaker and a microphone for her voice. Wiring is at the top of `sunrise.ino`.

- Testers (2026-10-18): a tester has a code of her own, added from owner view (`gc-config.js`, `add_sun_tester`, needs the ETL owner key) and kept as a fingerprint. It opens the panel and the fairies, keeps that tester's settings and chats apart from the owner's and from other testers (keys prefixed with the tester's id), and uses ETL's provider keys without ever showing them or being able to change them. `remove_sun_tester` takes the code away. This is the stand-in for per-sun codes, which are still not built.

- The preview as the front door (2026-10-19, Dr. O: make the panel so inviting a 19 year old asks when she can get a light or candle). With no access code the panel opens as a preview: a "Who should greet your morning?" picker (each need is one fairy's own job from the Court text), example answers with no voice, and the access code card moved to the bottom. "Want one?" takes an email through `sun-interest.js` into the `rising_sun_interest` store, one record per email, never sent anything. Dr. O reads the list with `GET /.netlify/functions/sun-interest` and `Authorization: Bearer <owner key>`. Not built: short recorded voice samples for the preview (add a file per fairy and a Hear button), and a page to read the list.

- Tiers (2026-10-19, Dr. O: "text, free for so many tries per day, no audio without an account. more options if ETL Lab member. discounts if ETL member"; "their greeting should be recorded so not costing after one try"). The preview talks for real through `sun-guest.js`, no access code. Who is asking comes from the ETL sign in (the Supabase session the rest of the site uses): guest (no sign in), account (signed in), member (signed in and `etl_credits.subscription_active`, the Lab membership). The limits are in one table, `LIMITS` in `sun-guest.js`: guest 10 text and no voice a day, account 30 text and 5 spoken, member 100 text and 30 spoken. They are placeholders for Dr. O to set. A guest is counted by address, kept only as a fingerprint, and a visitor's chat is kept only in their own page. `sun-greeting.js` records each fairy's hello and first question once, in the `rising_sun_audio` store, and serves it from there after, so a hello costs one spoken line however many play it. Not built: the discount for members (nothing sells these products yet, so there is no checkout to discount), and more options for members beyond bigger limits.

- Decided by Dr. O, 2026-10-19: the light and the candles are bought through the ETL Lab, and ETL Lab members get 15% off. Not built (no checkout yet); the panel's Want one? card already says it. A QR code on a table can tag signups: open the panel with `?s=comicon` (letters, numbers and dashes) and every email left from that page is stored with that source.

- The alert form (2026-10-19, Dr. O: "I need a form for people to be alerted when the lights and candles are available"). Public page `rising-sun/notify.html` (email, light or candle or both, an optional favorite fairy; `?s=` tags the source, `?p=light|candle|both` presets the choice). The same box sits on the panel. Both post to `sun-interest.js`. A first signup gets one short note from the work address (Resend, never blocks the signup) with a link to leave the list. Dr. O's page is `rising-sun/interest.html` (ETL owner key): the list, counts, copy the emails, download a spreadsheet, and write to the list with a test to her own address first. Everyone who left is skipped and every message carries its own link off the list. Needs RESEND_API_KEY, which the site already has.

- The web page (2026-10-19, Dr. O: "i need a web page, not just a panel"): `rising-sun/index.html`, at emerging-tech-lab.com/rising-sun/. A full page for the Rising Sun Court: hero, the seven fairies with their lore and gifts (each links to the panel with that fairy chosen, `panel.html?f=ash`), how they are with each other, the light and the candles (both marked Coming), how a morning goes, the free preview, the alert form, questions. It is plain HTML written from `personas.json` by a script, so a change to the lore needs the page written again. Old links that carried `?owner=`, `?k=` or `#k=` still land on the panel. The ETL homepage card still points at /rising-sun/, which is now this page.

- SEO and Google Analytics (2026-10-19, Dr. O: "I need it for SEO/GA"). The web page has a short title and description, a canonical address, share tags (Open Graph and Twitter), structured data (organization, page, breadcrumb, and the questions), image sizes and descriptions, one h1, and is in `sitemap.xml` with the alert page. The panel is `noindex` so the page is what search finds; the owner list page is `noindex` and not counted. Google Analytics 4 is on the web page, the panel and the alert page, using its own property `G-TC3L7MNC66` (switched from the ETL homepage property 2026-10-20). Events sent: `select_content` (a fairy was chosen), `cta_click` (try free, tell me), `chat_message` (a preview message, with the tier), `generate_lead` (an email left, with product, fairy and source). No email address is ever sent to Analytics. `tests/sun-seo.test.js` checks all of it.

- Palettes and no side padding on the web page (2026-10-19, Dr. O). The page has the same 26 Good Company and My Echo palettes as the panel, in a picker in the nav, remembered in this browser and shared with the panel (`sun_palette`). Light or dark is measured from each palette's background, and every palette is checked for contrast in `tests/sun-palettes.test.js`. Eight palettes had an accent too faint to read as text on the page and panel, so text accents use `--link`, which is the accent where it passes 4.5:1 and the palette's ink where it does not. The layout has no side padding: sections, the picture and the cards run edge to edge. `--inset` (12px, on `:root` in the page) is the only side space left, for plain lines of text; set it to 0 for none.
